# Decision log

One line per decision. Newest items go at the bottom.

- Item 0 (task status): no code change. The status select in `TasksView` already calls `mirrorTaskStatus`; verified in the browser that a change to `doing` sends `POST /api/backend/project-records/{project}/tasks/{task}/status` (200), the server returns `doing`, and the value survives reload.
- Item 0 (test data): verification used a test owner and test person in the local demo tenant; the browser test data was not committed.
- Item 1 (scope): this commit moves budget draws and releases to the server only. Invoices, payments, bills, credit notes and fund-request allocation are not moved yet and still change the browser store.
- Item 1 (money): budget amounts are whole paise in BIGINT columns with CHECK constraints (no negative balance, drawn never above allocated). The API takes integer paise; the screen converts rupees to paise once, at the request.
- Item 1 (concurrency): a draw or release locks its budget line with `SELECT ... FOR UPDATE`, checks what is left, writes the movement and updates the balance in one transaction.
- Item 1 (idempotency): draws and releases require an `Idempotency-Key` header, unique per tenant. A replay with the same line and amount returns the first result with 200; the same key with a different amount or line returns 409 `idempotency_conflict`. The browser sends a new key per click, so two separate clicks are two requests; a double click is blocked while the first is in flight.
- Item 1 (audit): each movement writes an audit row (`finance.budget_draw`, `finance.budget_release`, `finance.budget_allocation`, `finance.budget_line_created`). No timeline event is written, because budget lines belong to no project.
- Item 1 (demo mode): demo mode keeps the local path. In real mode the store's `drawBudget` and `releaseBudget` refuse, so budget money can only move through the server helper in `lib/finance-records.ts`.
- Item 1 (project flows): creating a project and closing a project now await the server draw and release. Creating a project checks its fields before the draw, so a refused project never moves money.
- Item 1 (test cleanup): the test cleanup truncates the two finance tables, because they reference tenants without a user foreign key that the existing cleanup relies on.
- Item 1 (known gaps): the draws list is a local copy; lines are created on the server when the screen first loads.
- Item 1 (fund allocation): approving a fund request calls `POST .../allocations` before its approval is recorded. The request id is the idempotency key (`fund-<id>`), so a retry or a double click allocates once. A failed allocation leaves the request as it was.
- Item 1 (movement kinds): migration 0021 adds `kind` (`draw`, `release`, `allocation`) with checks that tie each kind to its sign. Existing rows are backfilled from the sign of their amount, which is additive and drops no data.
- Item 1 (still local): invoices, payments, bills, credit notes, and the fund request workflow itself (who approved, status) are still stored in the browser store. Only the money moves are on the server. The draws list on screen is a local copy.
- Item 3 (transport): timeline entries arrive over server-sent events at `GET /v1/project-timelines/{key}/stream`. The browser opens it through the bridge with `EventSource`. The bridge streams the body without buffering and without the 45-second request timeout, and forwards `Last-Event-ID`.
- Item 3 (server loop): the stream reads new entries once a second in its own transaction under the member's tenant context. A non-member or removed member gets a `closed` event and the stream ends. This is a short database poll on the server, not on the browser; LISTEN/NOTIFY would remove even that and is a follow-up.
- Item 3 (resume): each entry is sent with its id. A reconnect sends `Last-Event-ID`, so entries are neither missed nor repeated. The stream ends after 5 minutes and the browser reconnects.
- Item 3 (fallback): polling every 8 seconds runs only while the stream is down, and stops when the stream opens again. Entries are added once by id, so the stream and a catch-up read cannot duplicate one.
- Item 3 (verified): a message posted by the API appeared on screen without a reload; the browser made no entry polls over 17 seconds while the stream was open. The fallback path was not exercised in the browser (it needs the stream to fail), so it is covered by code reading only.
- Item 2 (IT changes): IT change requests are a table on the server (`it_changes`), numbered per company as CHG-1002 onward. Request, decision and completion each need `settings:manage`, the permission the IT screen checks. A requester cannot decide their own change, a change is decided once, and only an approved change can be completed.
- Item 2 (timeline events): the timeline is for projects, and IT changes belong to no project. Each step therefore writes an audit row in its own transaction, not a timeline event. Modules without a project use the audit log as their history.
- Item 2 (names): the server returns the requester's and decider's names, because the screens show names and the users are looked up on the server.
- Item 2 (still local): the IT change log on screen and the other IT records (assets, access, licences, helpdesk, incidents, monitors) are still in the browser store. Operations, HR and Support are not started.
- Item 4 (scope): tickets only. The server holds each ticket's number, subject, priority, status, assignee and resolution. Conversations, handoffs, SLA timers and the customer link stay on the screen.
- Item 4 (permission): `agents:manage`, so owners and admins can change tickets and agents are refused. No support permission exists, and adding one needs role changes; switch to `leads:write` if agents should work tickets.
- Item 4 (order): each change goes to the server first, and the screen changes only after the server accepts it.
- Item 4 (keys): the screen's ticket id is the server's external key. Creating the same key again returns the existing ticket with 200, so a retry books it once.
- Item 4 (sync): on load the screen sends any ticket the server does not have yet, and copies the server's status, assignee and resolution onto its tickets. A refused create stays on screen and the next sync sends it.
- Item 4 (assignee): stored as the screen's user id text, not a foreign key, because the screen's user ids are not server user ids.
- Item 4 (audit): each step writes one audit row (`support.ticket_created`, `support.ticket_status_changed`, `support.ticket_assigned`, `support.ticket_resolved`) in the same transaction.
- Item 4 (cross-browser): a ticket opened in another browser appears here only after it exists on this screen.
- Item 4 (pre-existing gap, not changed): CRM records, including tickets, are shown only for a demo persona in the browser (`janus.demo-login`), so a real account sees no tickets on the Tickets screens. Browser checks used the bridge for the status steps.
- Item 1 rest (scope, partial): this change moves invoices with their lines, customer payments, and credit notes and write-offs (raise, approve, reject) to the server. Bills and bill payments stay local because their three-way match reads Operations purchase orders, which are not on the server yet. The fund-request approval chain also stays local; only its money allocation is on the server.
- Item 1 rest (money): the server works out every invoice total in paise. Each line's tax is rounded half-up; for same-state invoices an odd paisa of CGST goes to SGST, so the two halves always add up to the tax.
- Item 1 rest (numbers): the server numbers invoices `INV-<year>-<n>` and credit notes `CN-` or `WO-<year>-<n>`, unique per company. The screen shows the server's number.
- Item 1 rest (due): what is still due counts pending and approved credit notes, as the screen always did. A payment or credit note over that amount is refused on the server.
- Item 1 rest (approval): the person who raised a credit note cannot approve or reject it; the check uses the user id. Approver and rejecter names are stored for display.
- Item 1 rest (idempotency): every invoice, payment and credit note request sends an Idempotency-Key; a replay returns the first result with 200, and the same key with a different amount or kind returns 409.
- Item 1 rest (period locks): the server does not know the period locks yet. The screen checks them before it sends; a server-side lock is a follow-up.
- Item 1 rest (real mode): the server's invoice list replaces the screen's copy in real mode, so the demo invoices are no longer shown there, and bank lines matched to those demo payments no longer resolve.
- Item 1 rest (milestones): accepting a milestone bills it through the same invoice call, so the acceptance waits for the server and reports a refusal instead of changing the milestone.
- Item 1 rest (permission gate): the invoice form was gated on `invoice:create`, a demo-only name the server never issues, so no real account could create an invoice. It is now gated on `billing:manage`, the permission the server checks.
- Item 1 rest (ticket link): a credit note keeps the screen's support ticket id as text and does not check it against the server's tickets.
- Operations (scope, partial): this change moves the item master, batches, goods received and stock adjustments (request, approve, reject) to the server. Stock on hand is worked out from the server's movements. Dispatches, returns, transfers, counts, purchase orders and requisitions are not on the server yet; in real mode their stock steps are refused with a message, so nothing is saved locally and then lost.
- Operations (opening import): the first load of an empty ledger sends the screen's item master, batches and goods received once. It is refused once the company has any item, so it cannot add stock later. Item, batch and movement ids are kept, so purchase orders and dispatches still refer to the same items.
- Operations (stock rule): stock never goes negative. A negative adjustment is checked when it is requested and again when it is approved, because stock may have moved in between. Each change locks its item row, so two requests cannot both take the last unit.
- Operations (approval value): the server uses the default ₹10,000 approval line. The screen's workflow-rule setting is local, so changing it does not change the server; a per-company setting on the server is a follow-up.
- Operations (approval rules): the requester cannot approve or reject their own adjustment; the check uses the user id. Names are stored for display. Receipts and adjustments need `stock:adjust`.
- Operations (retries): receipts and adjustments send an Idempotency-Key. A replay returns the first result; the same key with a different item, quantity or location returns 409.
- Operations (screen): after each change the screen reloads the whole ledger from the server, so the balances shown are the server's, not the screen's own arithmetic.
- Operations (period locks): as for invoices, the screen checks the period lock before sending; the server does not know the locks yet.
- Operations (trail): approval and rejection lines are written to the server audit log; the on-screen trail does not add them in real mode.
- Dispatches (scope): dispatches with their challan lines, the pick, pack and ship checkpoints, proof of delivery, return authorisations and their inspection are on the server. Purchase orders, requisitions, transfers and physical counts are not yet, and their stock steps stay refused in real mode.
- Dispatches (stock): a dispatch takes its lines out of stock in the same transaction that books it. Lines for the same item and batch are added up before the check, so a dispatch cannot take more than is there. Items are locked in key order, so two dispatches cannot wait on each other.
- Dispatches (batches): a batch-tracked line needs a known batch, and an expired batch is refused. The expiry is checked against the server's date.
- Dispatches (checkpoints): picked, packed and shipped come in that order, each once, and each records the person who did it. Delivery needs the goods shipped first and a proof of at least three characters.
- Returns: a return can be authorised only for an item on the dispatch, and no more than the dispatched quantity. Good goods go back into stock only when inspected good; a damaged return is recorded and not restocked. A return is inspected once.
- Numbers: the server numbers dispatches `DN-<year>-<n>`, challans `DC-<year>-<n>` and returns `RMA-<year>-<n>`, unique per company.
- Retries: creating a dispatch or authorising a return sends an Idempotency-Key, so a retry books it once. Checkpoints and delivery are already single-step on the server, so a repeat is refused rather than repeated.
- Permission: dispatch and return steps need `stock:adjust`, the same permission as the stock ledger. The screen does not yet split pick and ship from receipts.
- Screen: after each dispatch or return change the screen reloads the ledger from the server.
- Pre-existing, not changed here: the Workflows view shows duplicate-key warnings in the browser console.
- Transfers and counts (scope): stock transfers between locations and physical counts are on the server. With them, the stock ledger covers every stock movement except purchase order receipts, which are the last piece of Operations; requisitions remain local.
- Transfers (stock): sending takes the stock out of the sending location in the same step, and receiving puts it in at the receiving location. The send checks stock at the sender and refuses a transfer to the same location. A transfer can be received once. A batch-tracked item needs its batch.
- Counts (adjustments): a count stores each line's system figure and counted figure, then books each difference as an adjustment in the same transaction. Under the approval value it is applied at once; above it, it waits for another person, exactly as a manual adjustment does. A difference can never take stock below zero, because the count holds the item lock and a counted figure cannot be negative.
- Counts (checks): a line counted twice, a batch that is not known, and a negative counted figure are each refused before anything is written. A retry with the same Idempotency-Key returns the first count and books no second set of adjustments.
- Numbers: transfers `TRF-<year>-<n>`, counts `CNT-<year>-<n>`, unique per company.
- Permission: transfers and counts need `stock:adjust`, as the rest of the ledger does.
- Screen: each change reloads the ledger from the server, so the system figures a count shows are the server's.
- Purchase orders (scope): purchase orders and goods received against them are on the server. Requisitions are still local, so ordering from an approved requisition is refused in real mode with a message; the purchase order can be raised directly. Bills, which match a bill to a purchase order, remain local.
- Purchase orders (receipts): a receipt can be at most what is still due on the line. Receipts for several lines of the same item are added up before the check. The order is locked, so two receipts cannot both take the same quantity. A receipt adds stock at the order's location and is a receipt movement in the ledger.
- Purchase orders (batch items): a batch-tracked item is refused on an order receipt and must be received with its batch from the stock ledger, as the screen already says; the order is not used for batch items.
- Purchase orders (numbers and keys): the server numbers new orders `PO-<year>-<n>`. An order keeps the id the screen gives it, so the opening orders from the demo keep their numbers and ids on the server.
- Purchase orders (opening import): the demo's purchase orders are part of the one-time opening import, so they are on the server with their numbers.
- Purchase orders (retries): raising an order and each receipt send an Idempotency-Key. A retried receipt returns the order with its received quantities unchanged.
- Permission: raising an order and receiving against it need `stock:adjust`, as the rest of the ledger does.
- Requisitions (scope): requisitions are on the server, with their approval and ordering as a purchase order. Bills and the fund-request approval chain are the remaining local parts of Finance and Operations.
- Requisitions (budget): approval reads the budget line on the server, which is allocated minus drawn, and refuses when the requisition's value (quantity times estimated rate) is more than what is left. The screen's figure is not sent, so it cannot approve money the server does not have.
- Requisitions (budget line): a requisition needs its budget line on the server. The Operations screen loads budget lines when it opens, so the lines are there before anyone raises a requisition.
- Requisitions (approval): the person who raised a requisition cannot approve or reject it; the check uses the user id. A pending requisition can be decided once.
- Requisitions (ordering): an approved requisition becomes one purchase order to the chosen vendor, delivered to the requisition's location. A second order is refused because the requisition is already ordered.
- Numbers and keys: requisitions are numbered `REQ-<year>-<n>` by the server. The screen's id is kept as the requisition's key.
- Permission: raising, approving, rejecting and ordering need `stock:adjust`, as the rest of the ledger does. Budget lines are still managed with `billing:manage` in Finance.
- Bills (scope): vendor bills and their payments are on the server, in paise. The fund-request approval chain is now the only Finance piece still local.
- Bills (three-way match): a bill raised for a purchase order is checked on the server against the goods received on that order. Goods not yet received refuse the bill; a bill that differs from the goods received is recorded but held, and a payment is refused until it matches. The match allows 2% of the received value, and at least ₹0.50, the same as the screen's default; the server does not yet hold a company's own tolerance rule, so a change to that rule on the screen does not change the server.
- Bills (payments): a payment locks its bill, refuses more than is still owed, and writes its audit row in the same step. A retry with the same Idempotency-Key returns the bill with the one payment; the same key with a different amount returns 409.
- Bills (demo data): in real mode the server's bill list replaces the demo bills, so the two demo bills no longer appear there, and bank lines matched to their demo payments no longer resolve (the same caveat as invoices).
- Bills (permission and numbers): bills need `billing:manage`, the same as the rest of Finance. Numbers are `BILL-<year>-<n>`, unique per company.
- Fund requests (scope): fund requests and their approval are on the server. An approval that puts money on a budget line allocates it in the same transaction, through the existing budget allocation, so the balance and the approval cannot disagree. Finance's records are now all on the server.
- Fund requests (limit): a request up to ₹50,000 is approved by its owner, which allocates at once. A larger one is approved by its owner, then by finance. The limit is the server's constant, matching the screen's; it is not a per-company setting yet.
- Fund requests (approvers): the person who asked cannot approve or reject their request, and the finance approver must be a different person from the owner's approver. A request that is approved or rejected cannot be decided again. A rejection is allowed only while the request is waiting.
- Fund requests (retries): raising a request sends an Idempotency-Key, and allocation is keyed on the request, so a retried approval cannot allocate twice.
- Fund requests (demo data): in real mode the server's list replaces the demo requests, the same caveat as for invoices and bills.
- Permission: fund requests need `billing:manage`, the same as the rest of Finance.
- Follow-ups (test isolation): the test cleanup now clears the job queue and raw event tables as well. Before, a job left pending by one test could be claimed by a later test's worker call. The two intermittent failures (a WhatsApp test and an ingestion test) failed once in roughly ten runs each after this change, and could not be reproduced on demand. Root cause not found; left open.
- Follow-ups (period lock): the period lock is on the server, per company. Every money and stock write dated on or before the locked date is refused on the server: budget moves (including fund allocations), invoices, payments, credit notes, bills, bill payments, stock receipts, adjustments and their approval, dispatches, transfers, counts, returns and purchase order receipts. The screen's check stays, so it can show the reason before a request is sent.
- Follow-ups (period lock dates): a stock write is dated by the server's date, not the screen's fixed day, because the server records the entry. A lock through a future date therefore blocks today's stock work.
- Follow-ups (rules): the adjustment approval value and the match tolerance are per company on the server. They default to ₹10,000 and 2%, as before, and the owner sets them on the screens, which save to the server. A bill's match and an adjustment's approval read the company's values, not constants.

- Team chat (search and files): search covers the messages in channels and in the searcher's own conversations, never another person's conversation, and it treats % and _ as plain text. - **Opening balances can be corrected (11 November 2026).** The Opening balances card lists what a company recorded, with Change (name, amount, due day) and Remove. A balance cannot drop below what has been paid or credited against it, and one with payments or credit notes cannot be removed: it is part of the books and is settled instead. Renaming onto another party's balance for the same day is refused, so re-importing an outstanding report still adds nothing twice. Each change and removal is audited with the before and after. - **One customer written two ways is counted once (11 November 2026).** Customers kept matches names without case, punctuation, "M/s" or company suffixes (Pvt Ltd, Private Limited, Ltd, LLP, OPC), so "M/S KAVITA STORES PVT LTD" from Tally is "Kavita Stores" from invoices; the name shown is the spelling with the most sales. Names that still look alike (difflib ratio 0.85 or more, or one name followed by more words, compared only within the same first three letters) are offered on the card, up to five per company, and "Same customer" records a merge in `portfolio_customer_merges` (migration 0069, per company under row-level security), which can be undone. "& Co" and "Company" are not stripped: "Gupta & Co" and "Gupta" may well be different firms. GSTIN matching waits for invoices to carry the customer's GSTIN.

- **GST to pay counts credit notes, carried credit and blocked credit (11 November 2026).** An approved credit note (kind "credit") takes off its share of the invoice's GST, worked out in proportion since a credit note keeps only a total; write-offs give none back, as GST has no bad-debt relief. A bill can be marked as blocked credit (Section 17(5): food, cars, personal use; `finance_bills.itc_blocked`, migration 0070) when recorded or later from Bills & payables, in an open period only, and its GST is shown but not taken. Input credit beyond a month's GST carries into the next month, folded month by month from the first books (`finance.overview.gst_carried`). Reverse charge, the 180-day rule and cash already paid are still not counted, and the card says so.

- **A bill between your companies is never recorded twice (11 November 2026).** Names on invoices and bills are matched as `core/names.party_key` matches them ("MEHTA RETAIL PVT LTD" is Mehta Retail), here, in the summary's sales and purchases between companies, and in customers kept. An invoice's bill is found by its number without case or separators ("inv/2026/0155"), or else, as a probable match, by a bill from that company for the same amount within 10 days, each bill used once. Recording the bill is refused (409 `already_recorded`) when either is found, except for a retry of the same request, which returns the bill it made. Bills are still not created automatically: the buying company may have it under another number, and a person checks a probable match.

- **A company document keeps its scan (11 November 2026).** One file per document, a PDF, JPEG, PNG or WebP up to 5 MB, told by its first bytes and never by its name, kept in `company_document_files` (migration 0072) under row-level security like Team Chat attachments, so no S3 setup is needed and the file goes wherever the database's backups go. Everyone who sees the company sees the register and the file's name; only people who may change documents (`portfolio:finance`) open, replace or remove it, and each download is audited. Removing a document removes its file. The web bridge passes the file through as it does attachments, and allows 64 KB over 5 MB for the multipart wrapping.
